# PROJECT_SPEC.md — Панель кабинетов Ozon + Wildberries

Главное функциональное ТЗ проекта. Любая крупная задача в этом репозитории должна
сверяться с этим документом — что уже решено, какие есть ограничения, что ещё не
сделано. Короткие текущие заметки/история решений — в `claude/ozon-dashboard-and-team.md`
в связанном проекте Claude (не в этом репозитории).

## Что это

Личный сайт-панель владелицы магазинов на Ozon и Wildberries: замена платному
сервису TrueStats, полностью под её контролем (свой репозиторий, свои ключи,
без ежемесячной подписки).

Показывает по каждому кабинету: заказы и выручку за 7 дней, чистую прибыль (по
себестоимости), процент выкупа, расходы площадки (комиссия/логистика/хранение),
рекламу и ДРР, риск нехватки остатков, короткий список задач на сегодня.
Обновляется сам каждое утро. При критичных задачах — уведомление в Telegram.
Раз в неделю — отдельный ИИ-разбор с выводами (не просто цифры).

## Архитектура

Статический сайт: GitHub Actions (по расписанию, раз в сутки + вручную) →
Python-скрипты забирают данные из API маркетплейсов → Jinja2-шаблон →
`index.html` → GitHub Pages.

```
scripts/
  common.py            — общие хелперы: форматирование, себестоимость из costs.json,
                          сборка задач на сегодня, отправка в Telegram
  fetch_ozon.py         — только функции получения данных Ozon (без рендера)
  fetch_wb.py            — то же самое для Wildberries
  build_dashboard.py     — точка входа: собирает оба кабинета в один index.html,
                          независимо друг от друга
  template.html.j2       — Jinja2-шаблон, параметризован по списку кабинетов
data/
  costs.json             — себестоимость товаров, заполняется пользователем вручную
  last_data.json          — кэш последних успешных данных по каждому кабинету
.github/workflows/update.yml — расписание + секреты
```

Каждый модуль `fetch_*.py` реализует единый контракт: `fetch_dataset()` (реальные
данные) и `demo_dataset()` (синтетика для `--demo`), возвращает словарь с ключами
`daily`, `velocity`, `sku_orders_7d`, `stocks`, `ads`, `returns`, `expenses`.

## Источники данных

- **Ozon Seller API** (`api-seller.ozon.ru`) — заголовки `Client-Id`/`Api-Key`.
  `/v1/analytics/data` (заказы/выручка/скорость продаж по SKU), `/v4/product/info/stocks`,
  `/v1/returns/list` (возвраты — метрика `"returns"` в analytics/data устарела, не
  использовать), `/v1/finance/accrual/by-day` (расходы, **один день за запрос**, поле
  `"date"`, не `date_from`/`date_to`).
- **Ozon Performance API** (`api-performance.ozon.ru`, НЕ `performance.ozon.ru` — старый
  домен отключён) — отдельные ключи `OZON_PERFORMANCE_CLIENT_ID`/`_SECRET`, OAuth2
  client_credentials.
- **Wildberries Statistics API** (`statistics-api.wildberries.ru`) — заголовок
  `Authorization: <токен>` (без Bearer). Лимит ~1 запрос/мин на метод — весь модуль
  укладывается в 3 запроса за прогон. Поля ответа не подтверждены вживую (ключ ещё не
  подключён на момент написания).

## Ключевые бизнес-правила

- **Себестоимость** — только через `data/costs.json`, вручную, никогда не через форму
  на сайте и никогда автоматически из API. Формат: `{"ozon": {offer_id: цена},
  "wb": {nmId: цена}}`. Товар без цены просто не участвует в расчёте прибыли — не
  ошибка.
- **Чистая прибыль** = выручка за 7 дней − себестоимость проданного − расходы площадки
  (комиссия+логистика+хранение) − расход на рекламу. Если `costs.json` для кабинета
  пуст — показывать "нужна себестоимость", не 0 и не ошибку.
- **Независимость кабинетов**: сбой Ozon не должен трогать данные/рендер Wildberries
  и наоборот. Статусы на кабинет: `ok` / `cached` (сбой, но есть кэш) / `not_configured`
  (секреты не заданы — мягкая карточка, не ошибка) / `unavailable` (сбой и нет кэша).
- **Честность вместо угадывания**: любая новая интеграция, не проверенная вживую,
  помечается в коде "НЕ ПРОВЕРЕНО ВЖИВУЮ" и обёрнута в try/except так, чтобы ошибка
  не ломала остальную страницу. После реального прогона — правка по тексту ошибки из
  лога Actions, диагностическая печать сырого ответа при необходимости.

## Архитектурные ограничения (не нарушать)

- Никогда не вводить и не использовать API-ключи/токены/пароли пользователя самому —
  только она сама вставляет их в форму GitHub Secrets.
- Код в репозиторий — только через GitHub "Upload files" (перетаскивание готового
  файла). Никогда через встроенный веб-редактор GitHub — он ломает отступы
  YAML/Python при построчном вводе.
- Любой новый файл перед загрузкой — проверить локально: `python3 -m py_compile`,
  прогон с `--demo`, при необходимости скриншот рендера.
- После пуша в main — GitHub Pages CDN обновляется с лагом ~1–2 минуты;
  `raw.githubusercontent.com/.../main/...` для мгновенной проверки без лага.
- Ozon Seller API: rate limit ~2 запроса/сек на `/v1/analytics/data` — не гонять
  workflow вручную слишком часто подряд при отладке.

## Статус на 27.08.2026 (вечер)

Готово и подтверждено вживую: Ozon-часть полностью (заказы, остатки, реклама/ДРР,
возвраты/процент выкупа). Wildberries — код готов и задеплоен, корректно показывает
"не подключено" (ключ `WB_API_KEY` ещё не добавлен пользователем).

Не завершено:
- Расходы площадки Ozon возвращают `state: "ok"` с нулевыми суммами — имена полей в
  ответе `/v1/finance/accrual/by-day` не подтверждены; добавлена диагностическая
  печать сырого ответа в лог Actions, ждёт разбора в одном из следующих прогонов.
- `data/costs.json` пуст — чистая прибыль не считается, пока пользователь не заполнит.
- Wildberries не проверен вживую (ключ ещё не добавлен) — вероятны мелкие правки
  после первого реального запуска.
- Telegram-уведомления (`TELEGRAM_BOT_TOKEN`/`TELEGRAM_CHAT_ID`) — ошибка
  `400 chat not found`, отложено по просьбе пользователя.
- Отзывы и вопросы — по-прежнему заглушка "скоро".

## Более широкий контекст: «ИИ-агентство»

Помимо сайта-панели, у пользователя есть набор готовых Claude-скиллов под задачи
продавца (разбор продаж, отзывов, рекламы, конкурентов, финансов, ассортимента,
остатков и т.д. — см. список скиллов в аккаунте). Идея — не заменять их сайтом, а
дополнять: сайт даёт цифры, скиллы (по расписанию через scheduled tasks) — разбор и
рекомендации, Telegram — канал доставки. Это направление развития, отдельное от
статического сайта, и не должно тянуть архитектуру сайта в сторону "динамического
приложения" без явного решения пользователя.
