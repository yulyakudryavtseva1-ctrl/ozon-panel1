# Profit Engine

Продолжение `docs/database.md` и `docs/connectors.md`. Profit Engine — единый и
единственный источник финансовой правды в системе: дашборд, отчёты и
AI-рекомендации всегда читают уже посчитанный `profit_daily`, а не пересчитывают
прибыль на лету из сырых заказов при каждом открытии страницы (§48 ТЗ:
Profit Engine — не то же самое, что Dashboard, и не должен зависеть от него).

## Когда считается

Отдельным шагом синхронизации, после того как за день отработали все
`sync*()` коннектора для конкретного `marketplace_account` (заказы, возвраты,
расходы площадки, реклама). Пересчитывает `profit_daily` не только за
сегодняшний день, но и **пересчитывает последние 7 дней при каждом прогоне** —
потому что у маркетплейсов данные по конкретному дню часто донасчитываются
задним числом (например, возврат, оформленный сегодня, относится к заказу
недельной давности; расходы по `finance/accrual/by-day` могут появляться с
задержкой). Без пересчёта задним числом цифры за прошлые дни будут тихо
устаревать и расходиться с тем, что реально покажет площадка в своём кабинете.

## Формула

```
net_profit = revenue
           − discounts
           − commission
           − logistics
           − advertising
           − returns_amount
           − storage
           − cost_of_goods
           − other_expenses
```

Все суммы — в рублях, округление до копеек внутри расчёта, до рублей только на
отображении в интерфейсе (не в хранимых данных — округлять до сохранения нельзя,
это накапливает ошибку при пересчётах).

Источники по каждому полю — из таблиц, которые заполняют коннекторы
(`docs/connectors.md`):
- `revenue`, `discounts` — из `orders`/`order_items`.
- `commission`, `logistics`, `storage` — из `marketplace_commissions`,
  `logistics_costs`, `storage_costs`.
- `advertising` — из `advertising_daily_stats.spend`.
- `returns_amount` — из `returns`, по цене на момент возврата (не текущей
  цене товара — если цена с тех пор изменилась, для честного расчёта нужна
  историческая цена; на Этапе 1 допустимо взять текущую `sku_prices` с явной
  пометкой в коде, что это упрощение до появления полноценной истории цен на
  уровне заказа).
- `cost_of_goods` — из `sku_costs`, себестоимость, действовавшая на дату
  заказа (`valid_from`/`valid_to`), не на сегодня.
- `other_expenses` — свободная категория для расходов, которые не относятся ни
  к одной из площадочных статей выше (задел на будущее, на Этапе 1 обычно 0).

## Неполные данные — `is_partial`

Если для проданного в этот день SKU нет записи в `sku_costs`, покрывающей
дату заказа, — этот SKU **не участвует** в `cost_of_goods`, а вся строка
`profit_daily` за день помечается `is_partial = true`. Дашборд обязан отдельно
показать «за N дней из 7 прибыль посчитана частично» вместо того, чтобы молча
занижать себестоимость нулём и показывать красиво выглядящую, но неверную
цифру — прямое продолжение принципа «честность вместо угадывания» из
`PROJECT_SPEC.md`.

То же самое правило — если у `marketplace_account` в этот день не было
успешной синхронизации ни по одному из нужных источников (заказы, расходы,
реклама): `profit_daily` за этот день не создаётся вообще, а не создаётся с
нулями. Ноль в интерфейсе должен означать «действительно ноль», а не
«не смогли посчитать».

## Агрегация на уровне клиента

`profit_daily.client_id` — уже сумма по всем `marketplace_account` этого
клиента (Ozon + WB вместе), а не по одному кабинету. Если у клиента несколько
кабинетов и хотя бы один из них в этот день `is_partial` — вся строка клиента
за день помечается `is_partial`, с указанием, по какому именно кабинету не
хватает данных (отдельное поле или связанная запись, не просто общий флаг без
объяснения — иначе непонятно, что чинить).

## Что Profit Engine отдаёт наружу

Только через свой API (`docs/api.md`, следующий документ) — Dashboard,
AI Core и отчёты не имеют прямого доступа к таблицам-источникам, только к уже
посчитанному `profit_daily` и (при необходимости drill-down на конкретный
SKU) к отдельному, тоже посчитанному, а не сырому, разрезу по SKU.
