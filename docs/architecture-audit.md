# Архитектурный аудит: «Marketplace Analytics OS»

Дата: 28.08.2026. Аудит проведён по запросу пользователя, до написания какого-либо
кода. Разобрано ТЗ `Marketplace Analytics OS.pdf` (40 страниц, разделы 1–74) в
сопоставлении с `PROJECT_SPEC.md` и `CLAUDE.md` текущего проекта (`ozon-panel1`).

## 1. Что на самом деле описывает это ТЗ

Это не доработка существующей панели, а техническое задание на **отдельный,
несравнимо более крупный продукт**: мультитенантная SaaS-платформа для управления
несколькими клиентами и их кабинетами на маркетплейсах из одного интерфейса, с
собственной базой данных, очередью фоновых задач, RBAC, версионированным REST API,
AI-агентами с доступом к данным через инструменты, и — что важнее всего —
«Action Engine», который умеет **сам менять цены и рекламные ставки** в кабинетах
через API маркетплейсов.

По объёму это — работа на команду инженеров на недели-месяцы промышленной
разработки, а не расширение статического сайта. Ниже — где это ТЗ противоречит
уже принятым решениям текущего проекта, что в нём слабо проработано, и какие в нём
реальные технические риски.

## 2. Главные противоречия с текущей архитектурой

### 2.1. Стоимость хостинга

Весь смысл текущего проекта — замена платной подписки TrueStats **бесплатным**
статическим сайтом (GitHub Actions + GitHub Pages, без сервера, без ежемесячных
платежей). Новое ТЗ требует: живой backend-сервер (Node.js, работает постоянно, а
не по расписанию), PostgreSQL, Redis, Docker-инфраструктуру, отдельные окружения
staging и production (§53, §54, §68). Всё это либо платный облачный хостинг, либо
сервер, который нужно администрировать. Это прямо возвращает ту же статью расходов,
от которой изначально уходили.

### 2.2. Модель доверия к API-ключам

Действующее правило (`PROJECT_SPEC.md`, `CLAUDE.md`): «никогда не вводить и не
использовать API-ключи/токены пользователя самому — только она сама вставляет их в
форму GitHub Secrets». ТЗ описывает таблицу `marketplace_accounts`, где ключи
клиентов хранятся в базе и постоянно используются работающим backend-сервером для
синхронизации и — в Action Engine — для **записи** в кабинет (§38, §47). Это другая
модель хранения секретов (шифрование в БД, а не GitHub Secrets), и вопрос, кто
разворачивает и обслуживает этот сервер, остаётся открытым.

### 2.3. Способ деплоя

Текущее правило: код заливается только через GitHub «Upload files» (перетаскивание
готового файла), никогда через встроенный редактор — он ломает отступы. Новое ТЗ
описывает полноценный CI/CD, миграции базы данных, Docker-сборки, несколько
окружений (§68, §69). Это принципиально другой процесс разработки и выкладки,
несовместимый с «загрузить файл через браузер».

### 2.4. Один аккаунт vs. несколько клиентов

Это — центральное противоречие, и оно **не техническое, а стратегическое**. Модель
`Organization → Users → Clients → Marketplace Accounts` с RBAC на 5 ролей имеет
смысл только если система обслуживает **нескольких разных клиентов** (агентство).
У Юли сейчас два своих кабинета (Ozon + WB) — ей не нужны организации,
роли-разрешения и переключение между клиентами.

При этом финальная фраза самого ТЗ (§74) прямо говорит: «...рабочую систему для
управления **несколькими клиентами** и маркетплейсами из одного интерфейса» — то
есть ТЗ по умолчанию описывает продукт для агентства, а не личный инструмент. Это
совпадает по духу с курсом «AI-менеджер для селлеров», который Юля упоминала
раньше как пример того, что она хочет. Вопрос, который нужно закрыть **до всего
остального**: это по-прежнему инструмент только для двух её кабинетов, или она
действительно хочет продукт, которым можно управлять несколькими клиентами (в том
числе, возможно, продавать доступ другим селлерам)? От ответа зависит, нужны ли
вообще RBAC, мультитенантность и Organization/Client-модель — если только для себя,
это лишняя сложность; если для нескольких клиентов — это необходимый фундамент.

## 3. Слабые места самого ТЗ

Независимо от вопроса выше, в самом документе есть пробелы, которые проявятся при
реализации:

- **Нет оценки стоимости хостинга.** Раздел «Технический стек» называет технологии
  (Postgres, Redis, Docker), но нигде не обсуждается, где это должно физически
  работать и сколько это будет стоить в месяц.
- **Нет модели шифрования ключей в состоянии покоя.** §62 требует, чтобы
  «marketplace credentials не попадали во frontend», но не описывает, как они
  шифруются в базе и кто держит ключ шифрования.
- **Синхронизация не учитывает реальные лимиты API.** §49–50 описывают общий
  pipeline и retry, но не используют уже добытые вживую в этом проекте цифры:
  Ozon `/v1/analytics/data` — не больше ~2 запросов/сек, Wildberries Statistics
  API — около 1 запроса/мин на метод. Без этого знания реализация синхронизации
  почти гарантированно упрётся в `429 Too Many Requests`, как уже было в текущем
  проекте.
- **Нет плана резервного копирования/восстановления** для базы данных, которая
  становится единственным источником финансовой правды (Profit Engine).
- **Не описан механизм аутентификации** (сессии? JWT? OAuth?) — упомянуты роли и
  права, но не то, как пользователь входит в систему.
- **Не затронуто законодательство о персональных данных** (152-ФЗ) — это
  становится актуальным, если система хранит данные нескольких независимых
  клиентов (это ещё один аргумент за то, чтобы явно решить вопрос из §2.4 в первую
  очередь).
- **Одна и та же методология разработки для разных по риску частей.** Текущий
  проект осознанно работает по принципу «задеплоить, посмотреть на реальную
  ошибку в логе, поправить» (`PROJECT_SPEC.md`, «честность вместо угадывания»).
  Это нормально для read-only дашборда: худшее последствие ошибки — неверная
  цифра на экране. Для «Action Engine», который меняет реальные цены и рекламные
  ставки, тот же подход недопустим: ошибка там означает реальные деньги (например,
  случайно выставленная нулевая цена или неконтролируемый расход на рекламу). ТЗ
  предусматривает подтверждение и audit log (§38, §41, §46), но не предусматривает
  отдельного, более строгого процесса разработки/тестирования именно для Action
  Engine.

## 4. Технические риски при реализации «как есть»

1. **Финансовый риск Action Engine.** Автоматическое изменение цены/ставки на
   реальном кабинете — это функциональность с прямыми денежными последствиями при
   ошибке. Нужны: жёсткие ограничения (максимальный шаг изменения цены за раз,
   дневной лимit на изменения), обязательный dry-run/предпросмотр перед
   выполнением, и по умолчанию ручное подтверждение каждого действия (в ТЗ это
   заложено — `ANALYZE → RECOMMEND → HUMAN APPROVAL → EXECUTE`, §46 — это
   правильное решение, важно не ослаблять его на практике).
2. **Кто обслуживает продакшн.** Живой сервер с базой данных требует резервного
   копирования, мониторинга, реакции на падения, обновления зависимостей. Юля не
   технический пользователь; либо это постоянно делает Claude/Cowork сессия по её
   просьбе, либо нужен другой ответственный — этот вопрос не решён ни в ТЗ, ни в
   текущем проекте.
3. **Масштаб и сроки.** Полная реализация ТЗ (26 шагов в §56: от Architecture до
   Deployment, включая полноценный RBAC, Action Engine, AI Core, admin-панель) —
   это месяцы работы, даже с помощью Claude. Ожидание «за одну сессию» нереалистично
   и должно быть явно проговорено.
4. **Безопасность мультитенантности.** Если направление — несколько клиентов, то
   ошибка изоляции между Client A и Client B (§62 сам это подчёркивает) — это не
   мелкий баг, а утечка чужих финансовых данных. Это резко поднимает цену ошибки
   по сравнению с текущим личным проектом.
5. **Дублирование с уже существующей автоматизацией.** У Юли уже есть набор
   Claude-скиллов (разбор продаж, отзывов, рекламы и т.д.), запускаемых по
   расписанию — фактически это уже работающий, более лёгкий вариант «AI Core» из
   ТЗ. Встраивание AI-агентов внутрь нового продукта (§43–45) может дублировать то,
   что уже работает отдельно, а не опираться на него. Стоит явно решить, заменяет
   ли новая система существующие скиллы или дополняет их.

## 5. Итог аудита

ТЗ технически последовательное и хорошо структурированное — как документ для
постройки коммерческой SaaS-платформы. Но оно описывает другой проект, чем тот,
что существует сейчас, и по объёму, стоимости хостинга, модели доверия к ключам и
процессу разработки прямо противоречит принятым в `PROJECT_SPEC.md` архитектурным
ограничениям. Главное несоответствие не техническое, а по назначению продукта:
рассчитан ли он на одну её пару кабинетов или на несколько клиентов. Предлагаемая
итоговая архитектура (см. `docs/architecture.md`) учитывает оба сценария и
предлагает поэтапный путь, который не обязывает сразу строить полную
мультитенантную версию.
