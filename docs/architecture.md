# Предлагаемая итоговая архитектура

Основано на аудите в `docs/architecture-audit.md`. Обновлено 28.08.2026 — три
открытых вопроса из первой версии этого документа закрыты пользователем напрямую,
ниже зафиксированы её решения и то, как они меняют план.

## Решено пользователем (28.08.2026)

1. **Хостинг и бюджет**: пользователь готова оплачивать хостинг. Выбран
   **Timeweb Cloud** (российский провайдер) — минимальный сервер (2 ядра, 2 ГБ
   памяти) на нём стоит примерно **900–1500 ₽/мес**, оплата обычной российской
   картой напрямую, без посредников. Это первый в проекте ежемесячный платёж
   (взамен бесплатного GitHub Pages). Домен — по желанию и не срочно: `.ru` ~
   200–300 ₽/год, `.com` ~ 1800 ₽/год; можно подключить позже, на старте подойдёт
   технический адрес вида `*.timeweb.cloud`.
2. **Мультитенантность**: нужен продукт **для нескольких клиентов** (агентство),
   а не только личный дашборд под её два кабинета. Это меняет план ниже —
   Organization/Client/RBAC закладываются **с первого этапа**, а не откладываются
   на отдельную развилку: переделывать однопользовательскую схему БД под
   мультитенантность задним числом дороже, чем спроектировать её так сразу.
3. **Action Engine**: старт — **только рекомендации, без автоматического
   выполнения**. Система анализирует данные и предлагает конкретные действия
   (например, «поднять цену с 1990 до 2190 ₽»), но ничего не отправляет в API
   маркетплейса без явного одобрения человеком. Возможность разрешить
   автоматическое выполнение для отдельных проверенных типов действий — на
   будущее, отдельным решением, не сейчас.

Эти решения расширяют рамки исходного `PROJECT_SPEC.md` (который описывал личный
однопользовательский сайт) — согласно правилу из `CLAUDE.md`, это зафиксировано
здесь как согласованное с пользователем расширение, а не тихая смена архитектуры.

## Этап 0 — текущий сайт остаётся как есть

Статический сайт (`ozon-panel1`, GitHub Pages) не трогаем и не заменяем, пока
новая версия не доказала, что работает. Он продолжает обновляться по расписанию
как сейчас. Это страховка: если новый этап забуксует, у Юли не пропадает то, что
уже работает.

## Этап 1 — фундамент: мультитенантный backend, только чтение

Отвечает на жалобу «нельзя полноценно работать» и сразу закладывает структуру под
нескольких клиентов, но без риска Action Engine:

- Backend (Node.js/TypeScript) + PostgreSQL на сервере Timeweb Cloud.
- С самого начала: Organization → Users → Clients → Marketplace Accounts,
  базовые роли доступа (даже если пока пользуется только сама Юля под ролью
  Owner) — чтобы добавление первого настоящего клиента позже не требовало
  переделки базы данных.
- Из ТЗ переносим то, что полезно независимо от масштаба: разделение
  Connector / Canonical Data / Profit Engine (§47–49 ТЗ) — упрощает добавление
  третьего маркетплейса позже; учёт уже известных вживую лимитов API (Ozon
  ~2 запроса/сек, Wildberries ~1 запрос/мин) прямо в дизайне Sync Engine, а не
  как общий retry без деталей.
- Реальные интерактивные действия вместо только просмотра: отметить задачу
  выполненной, редактировать себестоимость через форму в интерфейсе (вместо
  ручной правки `costs.json` в GitHub), вручную запускать синхронизацию,
  проваливаться из общей картины в конкретный SKU, переключаться между клиентами.
- Ozon и Wildberries подключаются как отдельные коннекторы (§47–48 ТЗ) — данные
  только читаются, никаких изменений в кабинетах маркетплейсов на этом этапе.
- AI-часть на этом этапе — **только рекомендации**: анализ данных, находки,
  предложения, без кнопки «выполнить». По возможности переиспользуем уже
  существующие Claude-скиллы Юли (разбор продаж/рекламы/остатков), а не
  дублируем их внутри нового продукта.

Результат этапа 1: рабочий интерактивный инструмент, готовый принять второго
клиента без переделки, с честными AI-рекомендациями — но ещё ничего не
делающий в кабинетах маркетплейсов автоматически.

## Этап 2 — Action Engine с обязательным подтверждением

Начинается только после того, как этап 1 стабильно работает:

- Каждое действие (`CHANGE_PRICE`, `CHANGE_AD_BID` и т.д.) обязательно проходит
  `ANALYZE → RECOMMEND → HUMAN APPROVAL → EXECUTE` (§46 ТЗ) — без исключений на
  старте.
- Жёсткие ограничения на масштаб одного действия (например, не более ±X% к цене
  за раз) и на количество действий в день.
- Обязательный audit log на каждое действие (§41 ТЗ, переносится как есть).
- Идемпотентность критических операций (§40 ТЗ, переносится как есть).

## Этап 3 — автоматическое выполнение (в будущем, по отдельному решению)

Разрешить системе выполнять действия без ручного подтверждения — но только для
узкого списка проверенных, доверенных типов действий, и только когда накопится
достаточно данных о том, что рекомендации на этапе 2 были верными. Не начинается
без отдельного явного решения пользователя.

## Что не берём из ТЗ (пока)

- Redis + BullMQ как отдельная очередь — на масштабе нескольких клиентов на
  старте избыточно; достаточно встроенного планировщика backend-а. Возвращаемся
  к этому вопросу, если нагрузка реально потребует отдельную очередь.
- Полноценные staging/production окружения с Docker Compose — на этапе 1 хватает
  одного окружения с ручной проверкой перед выкладкой; отдельное staging
  становится оправданным, когда появляются настоящие клиенты, чьи данные нельзя
  задевать тестами.

## Хостинг и бюджет

- Сервер: Timeweb Cloud, минимальная конфигурация (2 ядра / 2 ГБ) — ~900–1500 ₽/мес.
- Домен: не обязателен на старте; когда понадобится — `.ru` ~200–300 ₽/год или
  `.com` ~1800 ₽/год.
- Аккаунт на хостинге и оплату оформляет сама Юля (это её платёжные данные) —
  далее будет пошаговая инструкция, что именно нажимать.
