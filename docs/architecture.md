# Предлагаемая итоговая архитектура

Основано на аудите в `docs/architecture-audit.md`. Цель — дать Юле работающий
**инструмент**, а не только просмотр цифр (её исходная жалоба: «это просто
просмотр, а не инструмент»), не отказываясь при этом от полезных идей из ТЗ
«Marketplace Analytics OS», но не строя сразу всю мультитенантную SaaS-платформу,
пока не решён открытый вопрос из аудита (§2.4: один аккаунт или несколько
клиентов).

Разработка идёт поэтапно, каждый этап — самостоятельно полезный результат.
**Ни один этап не начинается без её подтверждения**, согласно правилу из
`CLAUDE.md`: если задача расширяет рамки `PROJECT_SPEC.md`, сначала сверяемся с
пользователем.

## Этап 0 — текущий сайт остаётся как есть

Статический сайт (`ozon-panel1`, GitHub Pages) не трогаем и не заменяем, пока
новая версия не доказала, что работает. Он продолжает обновляться по расписанию
как сейчас. Это страховка: если новый этап забуксует, у Юли не пропадает то, что
уже работает.

## Этап 1 — «личный инструмент» (без мультитенантности)

Отвечает на жалобу «нельзя полноценно работать», не вводя лишнюю сложность:

- Небольшой backend (Node.js/TypeScript или Python) + одна база данных
  (PostgreSQL или даже SQLite для начала) — **без Organization/Client/RBAC**,
  один пользователь, два кабинета (Ozon + WB), как сейчас.
- Реальные интерактивные действия вместо только просмотра: отметить задачу
  выполненной, отредактировать себестоимость через форму в интерфейсе (а не
  вручную редактировать `costs.json` в GitHub), вручную запустить синхронизацию
  из интерфейса вместо ожидания расписания, провалиться из общей картины в
  конкретный SKU.
- Из ТЗ переносим то, что полезно независимо от масштаба: разделение
  Connector / Canonical Data / Profit Engine (§47–49) — это хорошая идея, она
  упрощает добавление третьего маркетплейса позже; учёт уже известных лимитов API
  (Ozon ~2 запроса/сек, WB ~1 запрос/мин) прямо в дизайне Sync Engine, а не как
  общий retry без деталей.
- Никакого Action Engine на этом этапе — данные с маркетплейсов только читаются,
  ничего не изменяется автоматически.
- Хостинг: выбираем минимально затратный вариант (например бесплатный/дешёвый
  тир облачной платформы для маленького сервиса) — явно проговариваем с Юлей
  ожидаемую стоимость до начала, поскольку это первый этап, где появляется
  ежемесячный платёж (в отличие от текущего бесплатного GitHub Pages).

Результат этапа 1 — рабочий, интерактивный личный инструмент, полноценная замена
TrueStats по духу, но без RBAC, без Action Engine, без нескольких клиентов.

## Этап 2 — решение по мультитенантности (развилка)

Здесь останавливаемся и явно спрашиваем: нужен ли Юле продукт для нескольких
клиентов (агентство), или достаточно этапа 1 навсегда.

- **Если только для себя** — этап 2 не нужен, дальше сразу к этапу 3.
- **Если для нескольких клиентов** — только тогда строим то, что описано в
  ТЗ как Organization → Users → Clients → Marketplace Accounts, RBAC на 5 ролей,
  admin-панель (§4–§18, §66 ТЗ). Это отдельный, заметно больший объём работы,
  и его стоит начинать только когда есть реальный второй клиент/кабинет для
  проверки, а не «про запас».

## Этап 3 — Action Engine (автоматические действия), только после этапа 1/2

Самая рискованная часть ТЗ — по умолчанию максимально осторожно:

- Каждое действие (`CHANGE_PRICE`, `CHANGE_AD_BID` и т.д.) обязательно проходит
  `ANALYZE → RECOMMEND → HUMAN APPROVAL → EXECUTE` (как в §46 ТЗ) — без
  исключений на старте, никакого «автоматического выполнения» до того, как
  накопится доверие к рекомендациям.
  - Жёсткие ограничения на масштаб одного действия (например, не более ±X% к
    цене за раз) и на количество действий в день.
  - Обязательный audit log на каждое действие (§41 ТЗ — эта идея хорошая и
    переносится без изменений).
  - Идемпотентность критических операций (§40 ТЗ) — тоже переносится как есть.
- AI-часть (анализ, рекомендации) по возможности переиспользует уже существующие
  Claude-скиллы Юли (разбор продаж/рекламы/остатков), а не дублирует их внутри
  нового продукта — экономит время разработки и держит логику анализа в одном
  месте.

## Что не берём из ТЗ (пока)

- Redis + BullMQ как отдельная очередь — на масштабе одного-двух кабинетов
  избыточно; достаточно простого планировщика (как сейчас — GitHub Actions/cron
  или встроенный шедулер backend-а). Возвращаемся к этому вопросу, только если
  нагрузка реально потребует очередь.
- Полноценные staging/production окружения с Docker Compose — на этапе 1 хватает
  одного окружения с ручной проверкой перед выкладкой; отдельное staging
  оправдано начиная с этапа 2, когда ошибка задевает данные больше чем одного
  человека.
- Мультитенантный RBAC — см. этап 2, вводится только при подтверждённой
  необходимости.

## Открытые вопросы к Юле (нужны до начала кода)

1. Этап 1 подразумевает первый в этом проекте ежемесячный платёж за хостинг
   (взамен бесплатного GitHub Pages) — это приемлемо, и если да, какой бюджет
   ориентировочно комфортен?
2. Нужен ли в итоге продукт для нескольких клиентов (агентство), как в §74 ТЗ и
   в примере курса «AI-менеджер для селлеров», или речь только о её двух
   кабинетах?
3. Насколько активно она готова использовать Action Engine (реальные изменения
   цены/рекламы) — сразу после появления рекомендаций, или сначала долго
   смотреть на рекомендации без автоматического выполнения?

Дальнейшая детальная документация (`docs/database.md`, `docs/api.md`,
`docs/connectors.md`, `docs/profit-engine.md`, `docs/action-engine.md` и т.д. —
как в §73 ТЗ) пишется после того, как эти вопросы закрыты и этап 1 подтверждён,
а не раньше.
