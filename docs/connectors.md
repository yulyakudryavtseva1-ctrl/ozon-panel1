# Коннекторы маркетплейсов (Ozon / Wildberries)

Продолжение `docs/database.md`. Описывает, как площадки подключаются к общей
схеме — единый интерфейс сверху, специфика каждой площадки спрятана внутри
конкретного коннектора (§47–48 ТЗ: «Marketplace-specific логика не должна
попадать в Profit Engine, Dashboard, generic Products/Orders/SKU, Action
Engine — только внутрь коннектора»).

## Интерфейс MarketplaceConnector

Общий контракт для любой площадки:

```
connect()            — проверить и подготовить доступ (расшифровать credentials)
disconnect()          
testConnection()      — быстрая проверка, что ключи ещё рабочие
syncProducts()
syncOrders()
syncReturns()
syncFinances()         — комиссия/логистика/хранение
syncAdvertising()
syncInventory()
syncPrices()
executeAction(action)  — заглушка на Этапе 1, реальная реализация — Этап 2
```

Каждый `sync*()` возвращает единый результат: `{status: ok|error, records,
error?}` и обязательно пишет запись в `sync_jobs` (см. `docs/database.md`).
Ошибка в одном `sync*()` не должна прерывать остальные — тот же принцип
независимости, что и в текущем статическом сайте: если `syncAdvertising()`
упал, `syncOrders()` всё равно должен отработать.

Все синхронизации — **идемпотентные upsert'ы** по `(marketplace_account_id,
external_id)`: повторный запуск с той же площадки не создаёт дублей заказов,
возвратов и т.д., а обновляет существующую запись. Это важно, потому что
синхронизация по расписанию будет перезапускаться регулярно и может
пересекаться по датам.

Учётные данные (`marketplace_accounts.credentials_encrypted`) расшифровываются
только в памяти на момент вызова `connect()` и никогда не пишутся в логи —
диагностические `print`/`console.log` обязаны исключать поля с ключами, даже
при отладке (см. ниже пример с диагностической печатью в старом проекте — там
печатался только ответ API, не сами credentials, этот принцип переносится).

## OzonConnector

Базовый URL Seller API: `api-seller.ozon.ru`, заголовки `Client-Id` / `Api-Key`.

Уже подтверждено вживую в текущем статическом проекте и переносится без
изменений:

- **Заказы/выручка/скорость продаж** — `/v1/analytics/data`.
- **Остатки** — `/v4/product/info/stocks`.
- **Возвраты** — метрика `"returns"` в `/v1/analytics/data` **устарела**
  (`{"code":3,"message":"deprecated metrics used"}`) — использовать
  `POST /v1/returns/list` с фильтром `filter.logistic_return_date.{time_from,
  time_to}` (ISO8601), `limit`.
- **Расходы площадки (комиссия/логистика/хранение)** —
  `/v1/finance/accrual/by-day` принимает **один день за запрос**, поле
  `"date"` (`ГГГГ-ММ-ДД`), не диапазон `date_from`/`date_to` — иначе ошибка
  валидации. `syncFinances()` обязан делать по одному запросу на каждый день
  периода и суммировать результат, а не один запрос с диапазоном.
  Имена полей с самими суммами (комиссия/логистика/хранение) в ответе этого
  метода **ещё не подтверждены окончательно** в текущем проекте (см.
  диагностику ниже, задача перенесена из старого проекта, ещё не закрыта) —
  при переносе кода в `OzonConnector.syncFinances()` нужно either завершить
  эту диагностику на старом коде, либо повторить её здесь, прежде чем считать
  расходы решёнными.
- **Реклама/ДРР** — отдельный домен `api-performance.ozon.ru` (НЕ
  `performance.ozon.ru` — старый домен отключён), отдельные ключи
  (`Client ID`/`Client Secret`, не те же, что Seller API), OAuth2
  `client_credentials`. Подтверждено вживую, работает.

**Rate limit**: `/v1/analytics/data` — не больше ~2 запросов/сек
(`429 Too Many Requests ... "current max rate per sec.: 2"`, наблюдалось
вживую при частых ручных перезапусках). `Sync Engine` обязан выдерживать паузу
между запросами к этому методу, а не полагаться только на retry постфактум.

## WildberriesConnector

Базовый URL Statistics API: `statistics-api.wildberries.ru`, заголовок
`Authorization: <токен>` (без префикса `Bearer`).

**Не проверено вживую** — реальный ключ WB ещё не подключался ни к старому
статическому сайту, ни к новому backend'у. Код пишется по документации и
статьям, помечается «НЕ ПРОВЕРЕНО ВЖИВУЮ» и оборачивается в try/except так,
чтобы ошибка не роняла остальные кабинеты — тот же принцип, что и везде в
проекте. Почти наверняка после первого реального запуска потребуется мелкая
правка (имя поля, путь) — это ожидаемо, не повод откладывать интеграцию.

**Rate limit**: официально заявлено ~1 запрос/мин на метод — весь модуль
должен укладываться в минимальное количество запросов за один прогон
синхронизации (в старом проекте — 3 запроса за прогон, этот же принцип
переносится).

Реклама Wildberries (WB Advert API) — отдельный, более сложный API, не входит
в первую версию `WildberriesConnector`, добавляется отдельным шагом позже.

## Обработка ошибок и статус кабинета

`marketplace_accounts.status` — тот же принцип 4 состояний, что и в текущем
сайте:

- `ok` — последняя синхронизация прошла успешно.
- `cached` — синхронизация упала, но есть данные с предыдущего успешного
  запуска (используются вместо ошибки).
- `not_configured` — credentials ещё не введены — мягкая карточка, а не
  ошибка.
- `unavailable` — синхронизация упала и кэша нет.

Сбой одного `marketplace_account` (даже в рамках одного клиента, если у него
несколько кабинетов) никогда не должен мешать остальным — ни другому кабинету
того же клиента, ни тем более кабинетам других клиентов.
