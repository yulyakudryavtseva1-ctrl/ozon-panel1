# AI Core — Этап 1

Продолжение `docs/database.md`, `docs/profit-engine.md`, `docs/api.md`. Описывает,
как устроен AI-анализ на Этапе 1: только рекомендации, без исполнения (§43 ТЗ:
«AI не должен быть простым чатиком. AI работает поверх данных приложения»).

## Архитектура

```
Data → Analytics → Agent → Recommendation → Task
```

На Этапе 1 цепочка обрывается на `Task` — шаги `Action → Marketplace API`
(§43 ТЗ добавляет их дальше) не реализуются: агент может в лучшем случае
создать задачу «проверить/сделать вручную», но не может сам ничего изменить в
кабинете Ozon/WB. Это прямое продолжение решения из `docs/architecture.md`:
Action Engine — Этап 2, только с ручным подтверждением.

AI **не имеет прямого доступа к базе данных** — только через тот же API,
что описан в `docs/api.md`, обёрнутый в набор инструментов (§43 ТЗ: «AI
работает через строго определённые tools»). Это не искусственное ограничение
для красоты архитектуры, а конкретная защита: агент физически не может
случайно прочитать или изменить данные другого клиента мимо той же проверки
`client_id`, что стоит перед любым обычным запросом к API.

## Инструменты (Этап 1)

Подмножество списка из §44 ТЗ, без всего, что ведёт к исполнению:

```
get_client_metrics(client_id, period)
get_sales(client_id, account_id, period)
get_sku_profit(sku_id, period)
get_ad_metrics(account_id, period)
get_inventory(account_id)
get_price_history(sku_id)
create_task(client_id, title, description, priority, sku_id?)
```

`create_task` — единственный инструмент с побочным эффектом на Этапе 1, и он
создаёт запись в `tasks` (`docs/database.md`), не в `actions`. Агент не может
вызвать ничего из будущего Action Engine.

## Что должен уметь агент (Analytics Agent, §44 ТЗ)

1. анализировать период;
2. находить отклонения;
3. находить проблемные SKU;
4. определять возможные причины;
5. формировать рекомендации (`ai_recommendations`, `docs/database.md`);
6. создавать задачи, когда рекомендация требует конкретного действия человека.

## Не изобретать заново — использовать уже проверенную логику

У Юли уже есть набор Claude-скиллов, которые делают часть этой же работы
отдельно от сайта (`daily-sales-snapshot` — поиск аномалий по SKU,
`ad-analysis-recommendations` — трёхшаговый анализ рекламы,
`stock-out-forecast` — прогноз нехватки остатков, `unit-economics-analysis`,
`abc-xyz-analysis` и другие). Эти скиллы уже отражают её реальную методологию,
проверенную не один месяц — при реализации промптов и логики Analytics Agent
разумно опираться на них как на источник правды по методике анализа, а не
придумывать её заново с нуля внутри нового продукта. Что именно из них
переиспользуется буквально (текст промпта), а что просто как референс подхода —
уточняется отдельно на этапе реализации каждого конкретного типа рекомендаций,
не одним решением сразу на всё.

Отдельный открытый вопрос на будущее (не блокирует Этап 1): не дублировать ли
сами эти скиллы новым AI Core окончательно, а оставить оба пути параллельно —
это решается по факту использования, а не заранее.

## Доступ к модели

Через Timeweb AI Gateway (уже решено при выборе хостинга — `docs/architecture.md`,
раздел «Решено пользователем»), не напрямую к Anthropic API — так backend,
физически размещённый в России, не упирается в блокировку по IP.

## Стоимость и частота запуска

AI Gateway тарифицируется по токенам, в рублях — «Запустить AI-анализ» не
должен вызываться при каждом открытии дашборда. На Этапе 1 — запуск вручную
кнопкой (`POST /api/v1/clients/:id/ai/analyze`) плюс, по желанию, не чаще
одного раза в день по расписанию на клиента — не при каждом обновлении
данных. Точная частота — предмет отдельной проверки после того, как станут
видны реальные расходы токенов на первых прогонах.

## Жизненный цикл рекомендации

`ai_recommendations.status`: `new` → `viewed` → `accepted` (превращена в
`task` или, начиная с Этапа 2, в `action`) / `rejected`. Ничего не происходит
автоматически при переходе в `accepted` на Этапе 1 — превращение в задачу
делает человек, а не сам агент.
